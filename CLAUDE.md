# PeripheralHub: notes for Claude

A Windows tray app and .NET 8 library showing battery, online state and connection type (Wired / 2.4G dongle / Bluetooth) for the owner's peripherals. The README covers usage, device states, install, working alongside other apps and known limitations. This file holds the hard-won facts and decisions behind it.

## Layout
- **Plugin architecture (phase 1 of the owner's plan, 2026-10-27).** Device support that needs vendor protocols lives in plugins; the core only has the generic Bluetooth driver. **Owner's decision (2026-10-27): plugins stay bundled in the app repo and ship with the app for now; a bundled plugin turns on automatically (no prompt) the first time its device is detected (USB present / Bluetooth connected), and stays on (remembered).** Built. New devices are added with the `add-device` skill (see below), not an in-app tool. An online plugin catalog is not planned.
- `src/PeripheralHub.Sdk`: what plugins compile against (namespaces `PeripheralHub`, `.Devices`, `.Transport`, `.Plugins`): `DeviceSnapshot`, `IDeviceDriver`/`ScanContext`, `IDevicePlugin`/`PluginContext`/`PluginApi.Version`, `PluginManifest` (`plugin.json`), `VendorApp`, HID/BLE transport + Win32, `PolledHidSession`, `ReceiverDeviceDriver` (vendor app injected via ctor), `ConnectionResolver`, `CoreAudio` (Windows' sound endpoints, default-device switch).
- `src/PeripheralHub.Core`: `DeviceHub` (reads manifests; each scan first runs `ActivateDetected`, which loads + starts any dormant plugin `PluginMatcher` finds a device for, before drivers see the scan, so BT claims apply in the same scan; `GenericBluetoothDriver` runs last; plugin snapshots are stably sorted by `Kind`, generic BT after), `Plugins/PluginLoader` (`ReadManifests` runs no plugin code; `LoadCode` uses one `AssemblyLoadContext` per plugin; assemblies the host has, e.g. the SDK, come from the host), `PluginMatcher` (usb = non-Bluetooth HID present, honouring `manufacturer`; bluetooth = BLE/classic device with Connected), `ActivatedPlugins` (`%APPDATA%\PeripheralHub\activated-plugins.json`) and `PluginSet` (`Available`/`Active`/`Errors`; image/vendor-app/BT-claim lookups use active plugins only). A plugin that fails to start isn't retried until restart.
- `plugins/`: `PeripheralHub.Plugins.KreoIkarus` (`kreo-ikarus`), `.AulaF75` (`aula-f75`), `.SonyControllers` (`sony-controllers`), `.NothingEar` (`nothing-ear`), `.XboxControllers` (`xbox-controllers`), `.Monitors` (`monitors`), `.UsbHeadsets` (`usb-headsets`), each with driver + protocol + `plugin.json`. A manifest with `"alwaysOn": true` is turned on at every start without detection (Xbox: XInput has no USB/BT ID to match on; monitors: not HID or Bluetooth; USB headsets: any maker, found through Windows' sound devices). `plugins/Directory.Build.props/.targets` reference the SDK with `Private=false` (never ship a copy) and stage each plugin to `artifacts/plugins/<Config>/<id>/`; the App project copies those to `plugins\` in its output/publish folder. Manifest paths use `/` (backslashes get mangled by shell heredocs and need JSON escaping).
- Plugin folders: `<exe dir>\plugins` (built-in) and `%APPDATA%\PeripheralHub\plugins` (future installs); same id → higher version wins. Bluetooth `devices` entries in a manifest "claim" those IDs so the generic driver skips them; without the plugin the device shows as a plain BT device.
- `src/PeripheralHub.App`: WPF tray app (exe name `PeripheralHub`). It has the tray icon (`IconFactory`), panel (`FlyoutWindow`), widget (`WidgetWindow`), tiles (`DeviceTile`), view models, `PluginAssets` (vendor apps from `DeviceHub.Plugins`), `DeviceArt` (device pictures: `GenericPictures.xaml` drawings plus controllers filled from `Art\*.svg`), `VendorLauncher` and `AppSettings` (`%APPDATA%\PeripheralHub\settings.json`).
- `tests/`: xUnit, built from real captured frames plus plugin loading against the real plugin folders (234 tests as of 2026-11-02).
- `dotnet test` doesn't compile the App project (the tests don't reference it): run `dotnet build` (or build the App project) after UI changes, or the installer build is the first to hit App errors.
- The local JSON service and the console CLI were removed at the owner's request (2026-10-26; they're in git history before that). For hardware debugging, write a throwaway script instead of re-adding them (see "Checking the hardware").
- **Installer (owner's requirement 2026-10-27: users must never need commands).** **Releases come from GitHub Actions (owner, 2026-10-31):** **every release gets a `CHANGELOG.md` section first** (owner, 2026-11-01: "proper changelog from now"; `## X.Y.Z (date)`, one line per bullet, user-facing words; `build-installer.ps1` passes it to `vpk pack --releaseNotes`, which makes it the GitHub release description, and `-Publish` throws without one); pushing a tag `vX.Y.Z` (on main; only when the owner says, like any push) runs `.github/workflows/release.yml`: checks the tag is on main, builds, tests, then `build-installer.ps1 -Publish` with `GITHUB_TOKEN`; its "Run workflow" button is a trial run (installer kept as an artifact, nothing published). `.github/workflows/build.yml` builds + tests every push to main and every PR (restore needs `-p:Configuration=Release`, since the App sets its win-x64 RID only in Release). `build-installer.ps1 -Version x.y.z [-Publish]` (still works locally; the token is `$env:GITHUB_TOKEN`, else gh's login) publishes and packs with **Velopack** (`vpk` 1.2.161 as a local dotnet tool in `.config/dotnet-tools.json`; the `Velopack` NuGet in the App must be the same version) into `artifacts\installer\PeripheralHub-win-Setup.exe` + nupkgs. ## Devices and protocols (verified live on 2026-10-26/27)
- **Kreo Ikarus** mouse: cable `3554:FB0C`, 2.4G dongle `3554:FB0E`, BLE `3554:F533`. Vendor HID collection: usage page FF02/02 (`mi_01&col05`), 17-byte reports, report ID 0x08. Frame: `[08, cmd, …, checksum]` with checksum = 0x55 − sum(bytes 0..15). Cmd 03 = online (reply byte6). Cmd 04 = battery: byte6 = % (coarse 5% steps), byte7 = charging, bytes 8-9 = mV big-endian.
  - **Shown level = the Kreo app's method:** interpolate mV in its BatteryParam table (`KreoProtocol.VoltageTable`, from `Sys64\usersetting\Config.ini`), except while charging (voltage reads high, so use byte6). Small rises (≤ 3) while discharging are ignored as voltage wobble (`Session.Smooth`). Verified: 4072 mV = 93; the Kreo app showed 91–92 (its own extra smoothing; owner accepts the 1% gap).
  - **On the cable the level is real**, not pinned: about 85% on the dongle read 90% and charging on the cable.
  - The mouse pushes cmd 0x0A on status change, but NOT on wake from sleep. It sleeps about 60 s after the last movement.
  - Over BLE it exposes only the standard Battery Service level (GATT 1800/1801/180A/180F/1812, all checked): no charging flag and no vendor channel, so charging is impossible to get over Bluetooth.
- **AULA F75** keyboard: dongle `3554:FA09` (vendor FF02/02 `mi_01&col01`, 20-byte reports, report ID 0x13; frame checksum = sum of bytes 0..18), BLE `3554:FA07`, cable `258A:010C` (generic Sinowealth ID, product "Gaming Keyboard", no serial, firmware rev 1100, manufacturer "BY Tech", so the match also requires "BY Tech"; no battery over USB).
  - Cmd 07 (b2 = 1) = online (byte4 = len, byte5 = linked).
  - Cmd 0x4A = battery: byte5 = level, byte6 = flags (0x01 on battery, 0x10 external power; briefly 0x11 at plug-in, so test the bit). **While external power is set the level is not trustworthy (settled 2026-10-29):** (1) dongle + cable into the PC: at 82% it pushed `0A … 04 05 64 11` (100, flags 0x11) within 5 s, then the keyboard switched itself to wired mode (dongle link dropped, `258A:010C` appeared; no battery in wired mode). (2) Dongle + the keyboard's own cable on a phone charger: flag 0x10, the level isn't pinned but climbs from the real 87 by 1% every 15–25 s (87 → 93 in 100 s, far too fast for real charging, so it's voltage-inflated); after unplugging (state 0x01) it reads the inflated level (94) and drifts back down to the real level over a few minutes (owner); switching the keyboard off and on brings back the real 87 at once. The app has no smoothing for the F75, so this is the keyboard's own reading. (3) The same phone charger with a different cable set no flag at all (state 0x01, level 83 → 82): power-only cable or not charging. So hiding the level while 0x10 is set (greyed "was N%") is right. The 0x4A reply payload is only 2 bytes (level, state; e.g. `13 4A 01 00 02 54 01 …`), so there's no voltage or "settled" signal: nothing tells us a level is inflated after unplugging, and "was N%" itself is inflated if the charger goes back in while the level is still settling (size depends on charge time, ~7% seen after 3 min; never measured for longer charges). The README's Known limitations has a per-scenario table. (4) Bluetooth + charger (owner's observation): Windows' BLE level shows the same inflated rise, with no charging flag to hide it, so the tile shows it as live (accepted; no trend-based guessing). **Owner's handling (2026-10-29), which is the current code:** wired or dongle with 0x10 → bolt + greyed "was N%"; dongle without the flag (other cable) and Bluetooth → show whatever level the keyboard gives. The keyboard's behaviour is considered fully understood; don't re-test. 0x4A isn't in the vendor app; it was found by the community (ushineko/sanshoku #36, PyFlat/Device-Battery-Info #6).
  - Status pushes (cmd 0x0A, `AulaProtocol.ParseStatusPush`): kind 0x02 = link (`… 04 02 00` dropped / `02 01` back); kind 0x05 = battery after switching on (`… 04 05 <level> <state>`); kind 0x07 at power-on is unknown and ignored.
  - It sleeps after about 5 min.
- **DualSense** `054C:0CE6` (Edge `0DF2`), **DualShock 4** `054C:05C4/09CC`, Sony dongle `0BA0`. Battery comes from input reports (Linux hid-playstation/hid-sony formulas). Over Bluetooth, read the calibration feature (DualSense 0x05 / DS4 0x02) once to switch to full reports. Controllers are keyed by MAC; two real ones of the same model are numbered in first-seen order ("DualSense 2"). Charging works over Bluetooth with a power-only charger (verified). **Full-reports switch breaks plain-gamepad input (owner, 2026-10-29):** the calibration read puts a Bluetooth controller in full reports (0x31 / DS4 0x11) until it reconnects; there is no way back (SDL documents the same). Browsers (the Gamepad API: a gamepad tester site stopped seeing inputs as soon as PeripheralHub started) and DirectInput games only parse the basic 0x01 report. Windows has no battery property for these controllers. Owner chose: switch by default (battery is the point), menu switch **"Show Sony controller battery over Bluetooth"**, on by default (owner's final choice 2026-10-29, after trying a "Sony controller mode" Basic / Full picker with hint lines; label wraps to two lines; tooltip max 4 lines explaining Basic/Full; `AppSettings.ReadBluetoothControllerBattery` → mutable `PeripheralHubOptions.SwitchBluetoothControllers`, applied live), shown only while a Sony controller (054C + 0CE6/0DF2/05C4/09CC) is paired over Bluetooth (`PairedDevice` now carries VID/PID; `DevicesViewModel.SonyControllerPaired`). When off (basic mode), battery comes only from full reports another app (Steam, DSX, a game) turned on, else the snapshot has `BatteryUnavailable` and the tile shows the stored level as greyed "was N%" (same path as the F75 while charging), or greyed "Basic mode" with none. Turning it off while a controller is still in full mode needs a reconnect: the switch's tooltip always ends "After turning it off, turn the controller off and on." (owner, 2026-10-29: plain text, no condition; an amber line under the switch and a conditional tooltip line were tried first), and the tile's tooltip says it's still in full mode (session's last report ID). Windows pads basic 0x01 reports to the full input length, so over Bluetooth only 0x31/0x11 are parsed (reading the padding as a USB status showed 5%). DSX emulation is unaffected: the site reads the virtual cable-style DualSense.
- **Virtual controllers** (owner, 2026-10-28): game-streaming/remapping apps create fake "wired" controllers (punktfunk: "Punktfunk Virtual DualSense" = `SWD\VID_054C&PID_0CE6&MI_03\PF_PAD_0`, whose HID child looks like a USB DualSense; it reported a fixed 100%). `DeviceTree.FindVirtualOrigin` (SDK) walks a HID device's parents: reaching a hardware bus (`PCI\`, `ACPI\`, `ACPI_HAL\`) first = real; a software-created node first (`SWD\`, or `ROOT\` other than `ROOT\ACPI_HAL`, e.g. ViGEmBus) = virtual, named by that node (`HidDeviceInfo.Virtual`). Checked on the owner's PC: a plain "`ROOT\` = virtual" rule flagged all 25 real HID collections, since every real device sits under `ROOT\ACPI_HAL\0000`; with the hardware-bus stop, only punktfunk's virtual mouse (4 collections) was flagged. The Sony plugin shows them as plain "DualSense" (never numbered; real ones are numbered only among real ones) with `ConnectionType.Virtual`: a grey badge with a cloud icon reading **"Virtual (Creator)"** (`DeviceSnapshot.Source` = `VirtualOrigin.ShortCreator` (SDK): the creator device's Windows name minus generic words, **first word only**, e.g. "Punktfunk", "Nefarius"; nothing hardcoded; plain "Virtual" when unknown). **Hidden unless the tray's "Show virtual controllers" is ticked** (`AppSettings.ShowVirtualControllers`, default off, owner 2026-10-28; filtered in `DevicesViewModel`). Matching a virtual controller to the real one it mirrors (by correlating inputs) was discussed and turned down. Owner's choices 2026-10-28 (final): "Virtual" must always be in the badge; **no battery** for virtual controllers (punktfunk and DSX's emulation all read a made-up 100%; the tooltip says so); **no pin button** for them (`DeviceViewModel.CanPin`), and pins left on them from older versions are dropped (`DevicesViewModel`). Virtual ones are keyed `virtual-<software device id>`, have no Bluetooth MAC, and **count as connected while their software device exists**: punktfunk's only sends reports on changes, so the 4 s silence rule for real controllers made it vanish when idle. The probe template's `list` prints VIRTUAL(...) for such devices.
- **Xbox controllers** (plugin `xbox-controllers`, built 2026-10-28 without a real Xbox controller; owner: "skip Steam"). Uses **XInput** (`xinput1_4.dll`, 4 slots, battery type Wired/Alkaline/NiMH/Unknown and level Empty/Low/Medium/Full), polled each scan. `Windows.Gaming.Input` was tried and reports 0 controllers from a background process, so it's unusable. XInput doesn't say which device a slot is, nor adapter vs Bluetooth, nor charging, so: wired → "Wired", no battery; wireless → "Bluetooth" if a Microsoft (045E) gamepad is connected over Bluetooth, else "2.4G" (Xbox Wireless Adapter); the level is shown as a word (`DeviceSnapshot.BatteryLabel`, e.g. "Medium", icon filled to 5/25/60/100), or Windows' BLE % when there's exactly one Bluetooth Xbox controller. Emulated ones are found by listing XUSB interfaces (`EC87F1E3-C13B-4100-B5F7-8B84D54260CB`) and `DeviceTree.FindVirtualOrigin`; slots map to XUSB devices in order (tooltip says it's a best guess when real and virtual are mixed). Verified live only with DSX's Xbox 360 mode: XUSB `USB\VID_045E&PID_028E\2&…` under `ROOT\USB\0000` "Nefarius Virtual Gamepad Emulation Bus G2", XInput slot 0 Wired/Full → tile "Xbox Controller" + grey "Nefarius" badge, no battery. Ids `xbox:slot<n>`, model `xbox` (DSX's Xbox Series picture); slots seen this run stay as Disconnected. Real wired/adapter/Bluetooth paths are untested.
- **Monitors** (plugin `monitors`, always on, SDK API 2; owner's request 2026-10-29, verified live with an Acer VG240Y S on DisplayPort): `QueryDisplayConfig` (active paths only) each scan gives the EDID name, output technology (10 DisplayPort, 5 HDMI, 18 USB4/Thunderbolt tunnel = "USB-C"; USB-C alt mode usually reports plain DisplayPort; 17 indirect virtual, 0x80000000/6/11/13 built-in, 15 Miracast), desktop resolution and refresh rate. Owner's choices: tile shows name + teal video-link badge + "1920×1080 / 165 Hz" where the battery goes; the drawer has **brightness (VCP 0x10) and speaker volume (0x62) sliders, and the speaker icon toggles mute (0x8D: 1 muted, 2 not; verified on the Acer)**, nothing else (contrast, input switching, an HDR switch and an Asleep state were offered and turned down). Acer quirk (owner, 2026-10-29): unmuted while the volume is 0, it stays silent after the volume goes back up although it reports mute=2 vol=50; mute+unmute again fixes it, so the driver re-sends 1 then 2 whenever it raises the volume from 0. DDC/CI (`dxva2`, ~tens of ms per call) runs on a worker thread: once a minute, every 3 s while the drawer is open (`IWatchableDriver`), read back 2 s after a change; the slider sends at most every 150 ms (`LevelSender`) and the mouse wheel moves it by 5. Id = `monitor:<pnp id>:<EDID serial>` (serial text descriptor, else the 32-bit serial), so pins survive changing ports; falls back to the instance id. Name = maker from the PnP id (small table) + EDID name, numbered when two match. Software-made displays (`DeviceTree.FindVirtualOrigin` on `DISPLAY\…`, e.g. punktfunk's `PNK0001`) are `Virtual` and so hidden by "Show virtual controllers". Monitors are left out of the tray tooltip. A laptop screen is always named "Built-in display" (its EDID name is a panel part number) and gets no drawer (no DDC/CI); its brightness via WMI is not done.
- **USB headsets** (plugin `usb-headsets`, always on, any maker; owner's request 2026-10-29, verified with a CB CryoCore, C-Media `0D8C:0012`): from Windows' sound devices (MMDevice API) each scan: a USB headset = endpoints with enumerator `USB` sharing a container id, with both speakers and a mic (game controllers: a DualSense/DualShock 4 on USB is also a sound device with speakers and mic, its headphone jack, in the same container as its HID gamepad, so containers of HID usage 01/04-05 devices and adapter names containing "Controller" are skipped (owner's bug 2026-10-29); webcam mics, USB DACs, Bluetooth and software devices like Steam Streaming/Punktfunk, which are `ROOT` with container `00000000-0000-0000-ffff-ffffffffffff`, don't count). Name = adapter name minus Windows' "4- " install number. Id `usb-audio:<container>`. Tile: "Wired" badge, no battery, left out of the tray tooltip. **Owner's choice: the drawer has only "Set as default"** (makes its speakers and mic the default for all three roles via the undocumented `IPolicyConfig`, as SoundSwitch/EarTrumpet do; shows "✓ Default sound device" once it is). Offered and turned down: headset volume/mute, mic mute (+ tile mark), mic monitoring (sidetone). The CryoCore's chip exposes all of those as standard controls (speaker volume −37..0 dB; a sidetone mixer, muted, −23..8 dB; mic +23 dB max, AGC), and its only HID interface is consumer control (volume buttons), so no vendor channel (no lighting/EQ).
- Windows BLE battery: devnode property `{104EA319-6EE2-4701-BD47-8DDBF425BBE5} 2`. Connected flag: `{83DA6326-97A6-4088-9453-A1923F573B29} 15`. Paired-but-off devices keep a stale battery, so always gate on connected.

## Gotchas
- cfgmgr32 `CM_GETIDLIST_FILTER_PRESENT` returns nothing for BTHLE/BTHENUM; BT nodes must be located with `CM_LOCATE_DEVNODE_PHANTOM`, using the full instance id from the list (`BTHENUM\DEV_<MAC>\<instance>`): a bare `BTHENUM\DEV_<MAC>` is CR_INVALID_DEVICE_ID (30), with or without the phantom flag.
- Use ONE persistent reader per HID handle; a second pending read swallows replies.
- A receiver can't tell asleep from switched off; both just drop the link.
- Don't fuzz vendor commands: the command sets include flash writes.
- Every reply on a vendor channel reaches every app that has it open. That's why we pause while a vendor app runs, and why our sessions can update from replies to the vendor app's requests.
- **HidHide: only the tray toggle below** (owner, 2026-10-28: the first integration was built, removed entirely, then this minimal toggle requested). HidHide (DS4Windows/DSX) hides controllers from apps. Without the toggle ticked, a hidden controller isn't visible, so it disappears or shows Disconnected if pinned. **DSX turns cloaking on whenever it runs, even in native mode** (checked 2026-10-28: `--cloak-on` with both controllers on `--dev-hide`; opens fail with access denied (5) even at zero access, not a sharing violation, so it's HidHide, not DSX holding the device). **Tray toggle "Show hidden controllers" (owner, 2026-10-28, after removing the first integration):** shown only when HidHide is installed; ticked when our exe is on HidHide's allowed list (`Integration/HidHide` in Core: `Check` runs `HidHideCLI --cloak-state --inv-state --app-list`, no admin; `Parse` is tested). Clicking relaunches the exe elevated with `--hidhide-allow` / `--hidhide-remove` (`HidHideSetup`, one UAC prompt; it only runs `--app-reg`/`--app-unreg` and exits). State is re-read each time the tray menu opens. Inverse mode disables the item (tooltip explains). Uninstall removes our entry (`Installation.BeforeUninstall`, admin prompt). The Sony driver retries opening every scan and drops handles that can't be reopened, so toggling takes effect within ~2 s without a restart. No widget notice, no background monitor (the first version had both; the owner dropped them). Because an open handle survives hiding, the Sony plugin checks each scan whether its open controllers can still be opened afresh (`HidConnection.CanReopen()`, generic, not HidHide-specific) and closes those that can't, so switching DSX modes is reflected within ~2 s without a restart. DSX's emulated DualShock 4/DualSense hang off "Nefarius Emulation Bus G2" (`ShortCreator` → badge "Nefarius"); its Xbox 360 emulation shows through the Xbox plugin as "Xbox Controller" with the "Nefarius" badge. Facts worth keeping if it ever comes back: HidHide only blocks new opens/listings (a handle opened earlier keeps working until restart); the copy Velopack's Setup launches right after installing got through HidHide once while a normally started copy didn't (cause unknown); `HidHideCLI --cloak-state --inv-state --app-list --dev-list` reads state without admin but reads stdin without a console (close stdin); `--app-reg/--app-unreg` need admin; its lists live under the driver service key and vanish when HidHide is uninstalled. The removed code (notice + Allow, tray toggle, reconnect on hide-list changes) is in git history before 2026-10-28's "Remove HidHide integration" commit.
- **Memory (measured 2026-10-31, Release builds started through Explorer, read after 150 s):** Task Manager showed 87 MB with WPF's default GPU rendering, of which ~31 MB was the AMD driver's Direct3D buffers. `Program.Main` sets `RenderOptions.ProcessRenderMode = SoftwareOnly`: 48 MB, same or lower CPU for the drawer animations, and screenshots looked unchanged. Turning off concurrent GC plus TieredPGO (47 MB) and ReadyToRun (47.6 MB, exe 1.6 → 2.4 MB) made no difference, so both were left out. Second round: the GC then held ~30 MB for ~12 MB of live objects, because workstation GC sizes its gen0 budget from the CPU cache (16 MB here). The App csproj sets `TieredCompilation=false` (45 MB; 1,800 methods compiled instead of 10,500, and no tier-1 recompiles, which made the installed 1.0.0 creep up to 120 MB over an hour) and server GC with DATAS (`GarbageCollectionAdaptationMode=1`): **36 MB**, gen0 budget 2 MB, idle CPU unchanged (~1% of one core), ~18 more idle GC threads (~40). Didn't work: `GCgen0size` in runtimeconfig (.NET 8 reads it only from the environment), concurrent GC off with DATAS. `EmptyWorkingSet` drops the number to 12 MB but it refills to ~43 MB within a minute (cosmetic, not done). **Third round (owner saw 1.0.1 above 60 MB):** idle allocation was ~370 KB/s, and DATAS grows with allocation. An allocation trace showed ~85% was WPF: the hub publishes every scan (the paired list), and `DeviceViewModel.Update` raised `PropertyChanged("")` each time, so every tile re-read all bindings and `Parts` (a new list each read) rebuilt its row templates. `Update` now returns early unless `DiffersFrom` (all snapshot members are records), `Parts` is cached per snapshot, and the monitor mute/slider holds re-raise themselves when they expire (they relied on the 2 s refresh). `VendorApp.IsRunning` (3 drivers each scan, `Process.GetProcessesByName`) now shares one Toolhelp process-name list per 2 s. Result: ~50 KB/s (mostly Bluetooth `DeviceIds` lists), 27 MB vs 37 MB at 2.5 min. `HidConnection` used to copy every input report (~25–90 KB/s while a controller streams); since plugin API 3 the Sony plugin reads them through `ReportSpanReceived` (a span into the reused read buffer), and a copy is made only for a pending request or a `ReportReceived` listener (Kreo/AULA, a few replies a minute). Allocation traces: `dotnet-trace collect --profile gc-verbose`, then group `GCAllocationTick` events by type/stack with TraceEvent (a throwaway console app). To measure: `dotnet-counters`/`dotnet-gcdump` (install with `dotnet tool install --tool-path <scratch>`) attach to the Explorer-started process.
- PowerShell: `$Pid` is reserved; don't use it as a parameter name. `R` is an alias (Invoke-History), so don't name a helper function `R`.
